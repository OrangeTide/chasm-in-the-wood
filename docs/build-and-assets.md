# Build and assets

The project builds with Free Pascal and a modular Makefile, and bakes its reference art
into voxels at build time.

## The modular build

The top-level `Makefile` is thin. It declares the default goal and includes the fragments
under `mk/`, one file per concern:

```
mk/config.mk   toolchain, flags, unit search paths, SDL3 link path, OS and EXE
mk/engine.mk   the demo binary
mk/tools.mk    the voxelize tool
mk/assets.mk   the FBX to voxel asset pipeline
```

The build grows by adding a fragment, not by swelling one script. `config.mk` comes first
because it defines the toolchain the others use. `all` is declared before the includes so
it stays the default goal, with its real prerequisites filled in afterward.

Each source subsystem has its own unit search path in `config.mk`. Adding a subsystem adds
one `-Fu` there and nowhere else. OpenGL is loaded at runtime, so only SDL3 is linked, from
`SDL_PREFIX` which defaults to `/usr/local`.

Common targets: `make` builds the binary and its asset, `make run` runs it, `make tools`
builds the voxelizer, `make assets` bakes the voxel model, and `make clean` removes the
build tree.

## Install and packaging

`mk/install.mk` wires the game into a desktop from the same icon and binary. On Linux,
`make install` installs the `chasm` binary to `$(PREFIX)/bin`, the `chasm.desktop` launcher
to the applications directory, and the application icon into the hicolor theme at several
sizes. It honours `PREFIX` and `DESTDIR`, and `make uninstall` removes what it installed.

On macOS, `make bundle` assembles `build/Chasm.app` with the binary, an `Info.plist` whose
version comes from the `VERSION` file, and a `chasm.icns` built from the icon with `sips`
and `iconutil`.

The icon is `packaging/chasm.png`, the gold-on-green wordmark. Its font is recorded in
`PROVENANCE.md`. The installed binary still reads its `content/` data relative to the
working directory, so a menu-launched install needs that data resolved separately. That
work is tracked in `ROADMAP.md`.

## The asset pipeline

The reference character ships as an FBX, which is impractical to parse in Pascal. The
pipeline converts it at build time, in `mk/assets.mk`:

```
Character.fbx  --assimp-->  character.obj  --voxelize-->  character.vox
```

`assimp` turns the FBX into an OBJ, and the `voxelize` tool rasterizes the OBJ into a
MagicaVoxel `.vox`. Both run only at build time; the committed product is the `.vox`.
`assimp` must be installed to rebuild the asset. See [Voxels](voxels.md) for the voxelizer
itself.

The build tree, the extracted FBX, the intermediate OBJ, and the generated `.vox` are all
build output and are ignored by git.

## Tests

`make test` compiles and runs each `tests/t_*.pas`, standalone programs that exit
non-zero on failure. They cover the parts that have no GL dependency: the seeded RNG,
dungeon generation (reproducibility, a connected room graph, a walkable spawn), and
chunk streaming.

The streaming test is the reason for the mesh backend seam. It wires the null backend
from `meshbackend` so the world builds and frees chunks with no GL context, then walks
the player across a large level and checks that chunks load near the player, evict when
left behind, reload on return, and that the resident set stays bounded over repeated
trips. This verifies the load and evict cycle without a window. See
[Rendering](rendering.md) for the seam and [World streaming](world-streaming.md) for the
cycle it tests.

## Art policy

The project prefers purchased or human-made art and audio. The reference character is CC0
human-made art. Art from purpose-built generative voxel tools, for example VoxelAI or
Hyper3D, counts as production art, subject to confirming the generated asset's licence
before the release that ships it. Art generated by a coding assistant is only ever a
placeholder. Any placeholder, such as the flat dungeon tile colours generated in code, is
listed in `ROADMAP.md` to be replaced with authored art before the release that ships it.

## Versioning and releases

The game version lives in the top-level `VERSION` file. `ROADMAP.md` groups planned work by
minor release with an unassigned section, and `CHANGELOG.md` follows Keep a Changelog with
in-progress work under Unreleased. Each minor release updates the changelog and gets an
annotated git tag whose message is that version's changes. The release process covers the
game, not the voxel tooling.

Commit messages keep the subject at or under 50 characters and wrap the body at 72, which a
`commit-msg` hook enforces.
